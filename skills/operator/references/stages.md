# 단계 모델 — 아이디어에서 운영까지

pass 가 "하루치 작업"이라면 단계는 "프로젝트의 시기"다. 지금 단계는 `.operator/stage.json` 에 있고,
`op` 만 바꾼다(가드가 직접 편집을 막는다). 단계가 정하는 것은 넷이다.

| 항목 | 뜻 |
|---|---|
| 목표 | 이 단계에서 알아내거나 만들 것 |
| 할 수 있는 일 | 승인 큐에 올릴 수 있는 종류와 기본 pass 단계 |
| 산출물 | `.operator/stages/<단계>.md` (만들기는 마일스톤 목록도) |
| 통과 조건 | `op stage check` 가 검사. 통과해도 넘기는 건 사람 (`op stage advance`) |

```
발견 → 검증 → 만들기 → 운영 → 배우기 → (문서의 "다음 단계:" 한 줄: 운영 | 만들기 | 발견)
                ↑ 검증의 "결정: 수정" 은 발견으로
```

## 명령

| 명령 | 누가 | 하는 일 |
|---|---|---|
| `op stage` | 누구나 | 지금 단계, 목표, 올릴 수 있는 것, 산출물 상태, 넘어가기 조건 |
| `op stage doc [단계]` | 에이전트 | 산출물 템플릿 만들기 (있으면 그대로 둠) |
| `op stage check` | 에이전트 | 조건 검사. 통과하면 exit 0 |
| `op stage history` | 누구나 | 이동 기록 (언제, 어디서 어디로, 이유) |
| `op stage advance` | **사람**, 대화형 터미널 | 조건을 다시 검사하고 다음 단계로. 문서는 `stages/history/` 에 사본과 해시가 남는다 |
| `op stage back --to 단계 --reason "..."` | **사람** | 되돌리기. 이유는 `op stage` 에 보이고 에이전트가 먼저 반영한다 |
| `op stage set 단계` | **사람** | 아무 단계로 바로 (기존 프로젝트를 단계 모델로 옮길 때) |
| `op milestone add/list/done/reopen` | 에이전트 | 만들기 단계의 작업 단위. `done` 은 검사 명령이 exit 0 일 때만 |
| `op metric add/list` | 에이전트·사람 | 배우기 단계의 숫자. 자동 집계(보낸 수, 거절 수)도 함께 보여 준다 |

`op init` 은 새 프로젝트를 발견 단계로 만든다. 이미 운영 중이면 처음에 `op init --stage operate`.
`stage.json` 이 없는 0.4 이전 프로젝트는 단계 모델을 쓰지 않는 것으로 보고 운영과 똑같이 동작한다.

## 단계별 통과 조건

| 단계 | 문서 섹션 (각 10자 이상, 빈칸 표시 없음) | 추가 조건 |
|---|---|---|
| 발견 | 문제, 고객, 제안, 성공 지표 | — |
| 검증 | 근거, 결정 | 출처 URL 3개 이상, `결정: 진행|수정|중단` 한 줄 (중단이면 넘어가지 않음) |
| 만들기 | 범위 | 마일스톤 1개 이상, 전부 통과. `verify.site.command` 가 있으면 빌드 성공 |
| 운영 | (없음) | 이 단계에 들어온 뒤 보낸 항목 1개 이상 |
| 배우기 | 결과, 다음 | 이 단계에서 기록한 지표 1개 이상, `다음 단계: 운영|만들기|발견` 한 줄 |

섹션 제목은 영어도 된다 (Problem, Customer, Offer, Success metric, Evidence, Decision, Scope, Results, Next).
템플릿의 `<!-- -->` 주석은 검사에서 무시하므로 지우지 않아도 된다.

## 예시 — 동네 빵집 예약 앱

**발견** `.operator/stages/discover.md`

```markdown
## 문제
사장님이 전화로 예약을 받느라 손님 응대를 못 한다. 지금은 노트에 적는다.
## 고객
마포구 1인 운영 빵집 사장님. 상인회 단톡방에서 만난다.
## 제안
월 1만 원 예약 페이지. 문자 한 통으로 확인. 수수료 없음.
## 성공 지표
첫 달 유료 가입 사장님 3명.
```

**검증** — 리서치 pass 후

```markdown
## 근거
네이버 예약은 수수료가 부담이라는 글이 많다 (https://...). 경쟁 서비스는 월 2만 원 (https://...). ...
## 결정
단순하고 수수료가 없으면 차별점이 있다. 다만 카카오톡 알림 요구가 보여 범위에 넣을지 만들기에서 정한다.
결정: 진행
```

**만들기**

```bash
op milestone add "예약 폼과 저장" --test "npm test -- booking"
op milestone add "사장님 알림 문자" --test "npm test -- notify"
op milestone done 1 ; op milestone done 2
```

첫 배포는 `type: site` 초안을 `--action "npm run build && wrangler deploy"` 로 승인 큐에 올린다.

**운영** — 매일 pass. 상인회용 소개 글, 사장님 10명에게 보낼 메일.

**배우기**

```bash
op metric add emails_sent 10 --source "op metric list 자동 집계"
op metric add replies 2 --source "메일함"
op metric add signups 1 --source "관리자 화면"
```

```markdown
## 결과
가입 1명. 목표 3명에 못 미쳤다. 답장 2통 모두 카카오톡 알림을 원했다.
## 다음
알림을 카카오톡으로 바꾸고 같은 10명에게 다시 연락한다.
다음 단계: 만들기
```

## 에이전트가 지킬 것

- 단계에 맞지 않는 요청을 받으면 거절하지 말고, 지금 단계와 이유를 말한 뒤 사람이 단계를 옮길지 정하게 한다.
- 발견 단계에서 답을 지어내지 않는다. 사용자가 모른다고 하면 "모름"으로 두고 검증 단계의 조사 항목으로 넘긴다.
- 검사 명령은 실제로 기능을 확인해야 한다. `true`, `echo`, `exit 0` 은 거부된다.
- 지표는 사용자가 알려 주거나 실제로 확인한 숫자만 기록한다.
